# Практическая работа 2 — Kafka на Java

Приложение отправляет JSON-сообщения в топик `messages` и читает их двумя способами: по одному и пачками. Топик содержит **3 партиции**, у каждой **2 реплики**.

## Как всё устроено

Docker Compose запускает ZooKeeper, три брокера Kafka (`kafka1`, `kafka2`, `kafka3`), Kafka UI и два экземпляра Java-приложения. В каждом экземпляре работают один продюсер и два консьюмера в отдельных потоках.

```text
app × 2
  MessageProducer ────────────────> messages (3 партиции, 2 реплики)
  MessageSingleConsumer <────────┘  группа single-group
  MessageBatchConsumer  <────────┘  группа batch-group
```

Группы `single-group` и `batch-group` независимо читают одни и те же записи. Внутри каждой группы два консьюмера делят между собой три партиции. Поэтому каждую запись читает один участник каждой группы, а не каждый контейнер приложения.

## Файлы и классы

Все Java-классы находятся в `src/main/java`.

| Файл | Назначение |
| --- | --- |
| `Application.java` | Точка входа. Запускает продюсер и двух консьюмеров в трёх отдельных потоках. |
| `Message.java` | Модель с полем `text`. Конструктор без аргументов создаёт текст с локальным временем процесса; конструктор с `@JsonCreator` восстанавливает объект из JSON. Lombok генерирует getter. |
| `MessageProducer.java` | Создаёт сообщение примерно каждые 100 мс, сериализует его в JSON и асинхронно отправляет в `messages`. Ключ отсутствует, партицию выбирает Kafka-клиент. Callback выводит результат доставки. |
| `MessageSingleConsumer.java` | Читает не больше одной записи за `poll()`, десериализует её в `Message` и выводит в лог. Использует автоматический коммит offsets. |
| `MessageBatchConsumer.java` | Читает до 10 записей за `poll()`, выводит их в цикле и один раз вызывает `commitSync()` после непустой пачки. |
| `pom.xml` | Настраивает Java 17, Kafka Clients 3.9.0, JSON-библиотеки Confluent/Jackson, Lombok и консольные логи SLF4J. Maven Shade собирает зависимости и точку входа в `target/kafka-app.jar`. |
| `Dockerfile` | Сначала собирает JAR в образе Maven с JDK 17, затем копирует его в образ с JRE 17 и запускает через `java -jar app.jar`. Тесты при сборке образа пропускаются. |
| `docker-compose.yaml` | Описывает кластер, общую сеть, два экземпляра приложения (`deploy.replicas: 2`) и Kafka UI. |
| `topic.txt` | Содержит команду создания топика и сохранённый результат его описания. |

Пример сообщения в Kafka:

```json
{"text":"message-2026-10-28 17:00:00"}
```

Используются `KafkaJsonSerializer` и `KafkaJsonDeserializer`. Schema Registry для этого формата не нужен; соответствующий сервис в Compose закомментирован.

## Основные настройки

Назначение параметров также пояснено комментариями в коде.

| Компонент | Настройка | Что она даёт |
| --- | --- | --- |
| Все клиенты | `KAFKA_BOOTSTRAP_SERVERS` | В Docker: `kafka1:9092,kafka2:9093,kafka3:9094`. Без переменной окружения: `localhost:9092,localhost:9093,localhost:9094`. |
| Продюсер | `acks=all` | Ожидает подтверждения от всех текущих синхронных реплик (ISR). Ранее записанное в коде `acks=1` переопределяется этим значением. |
| Продюсер | `retries=Integer.MAX_VALUE` | Разрешает повторные отправки при временных ошибках. |
| Продюсер | `delivery.timeout.ms=120000` | Ограничивает время доставки с повторами двумя минутами. Окончательная ошибка выводится в callback. |
| Одиночный консьюмер | `group.id=single-group`, `max.poll.records=1` | Отдельная группа, не больше одной записи за вызов `poll()`. |
| Одиночный консьюмер | `enable.auto.commit=true` | Offsets сохраняются автоматически периодически, а не сразу после каждого сообщения. |
| Пакетный консьюмер | `group.id=batch-group`, `max.poll.records=10` | Отдельная группа, не больше 10 записей за вызов `poll()`. |
| Пакетный консьюмер | `enable.auto.commit=false` | Offsets подтверждаются вручную после обработки всей полученной пачки. |
| Пакетный консьюмер | `fetch.min.bytes=1000`, `fetch.max.wait.ms=1000` | Брокер ожидает накопления нужного объёма данных не дольше секунды; ответ может оказаться меньше указанного объёма. |
| Оба консьюмера | `auto.offset.reset=earliest` | Читают с начала доступных данных, если у группы нет действительного сохранённого offset. |

У клиентов используется `try-with-resources`: при выходе из блока клиент закрывается. Консьюмеры логируют ошибки десериализации и повторяют чтение, продюсер логирует ошибки сериализации и доставки. Обработка сообщения в этой работе — вывод его содержимого в лог.

## Запуск

Нужны Docker с запущенным Docker Engine и Docker Compose. Java и Maven на компьютере не обязательны: сборка выполняется внутри Docker.

Все команды выполняются из папки `basic-kafka-java`.

### 1. Запустить инфраструктуру

```shell
docker compose up -d zookeeper kafka1 kafka2 kafka3 kafka-ui
```

Проверить, что брокеры готовы принимать запросы:

```shell
docker compose exec kafka1 kafka-broker-api-versions --bootstrap-server kafka1:9092,kafka2:9093,kafka3:9094
```

Если брокеры ещё запускаются, повторить проверку через несколько секунд. `depends_on` в Compose задаёт порядок старта контейнеров, но не проверяет готовность Kafka.

### 2. Создать и проверить топик через консоль

```shell
docker compose exec kafka1 kafka-topics --bootstrap-server kafka1:9092 --create --topic messages --partitions 3 --replication-factor 2
docker compose exec kafka1 kafka-topics --bootstrap-server kafka1:9092 --describe --topic messages
```

Если топик уже создан, достаточно выполнить `--describe`. Ожидается `PartitionCount: 3`, `ReplicationFactor: 2` и три строки партиций с двумя брокерами в `Replicas` и `Isr`. Лидеры и порядок реплик могут отличаться от сохранённого примера в `topic.txt`.

После добавления третьего брокера реплики существующего топика автоматически на него не переносятся. В `topic.txt` сохранён вывод с брокерами 1 и 2 — это допустимо и при работающем третьем брокере. Для актуального результата выполните `--describe` и обновите сохранённый вывод в `topic.txt`.

В используемом Docker-образе утилита называется `kafka-topics`; это аналог `kafka-topics.sh` из задания. Автоматическое создание топиков отключено, поэтому топик нужно создать до запуска приложения.

### 3. Собрать и запустить два экземпляра приложения

```shell
docker compose up -d --build --scale app=2 app
docker compose ps
docker compose logs -f app
```

В Compose уже указано `deploy.replicas: 2`; `--scale app=2` явно задаёт то же количество при запуске. В списке контейнеров должны быть два экземпляра `app`.

Остановить просмотр логов можно через `Ctrl+C`, контейнеры продолжат работать.

## Как проверить результат

1. Проверить через `docker compose ps`, что запущены `kafka1`, `kafka2` и `kafka3`. Команда `kafka-broker-api-versions` из инструкции выше должна показать брокеры с ID 1, 2 и 3. Выполнить `--describe`: у топика три партиции и по две реплики.
2. В логах продюсера найти `Sent: topic=messages, partition=..., offset=...` — callback получил подтверждение отправки.
3. В логах потока `single-message-consumer` найти `Message received` с текстом сообщения, партицией и offset. В потоке `batch-message-consumer` найти такие же записи. Сопоставлять сообщения нужно по паре **partition + offset**: текст с временем может повторяться.
4. В логах пакетного консьюмера найти `Poll completed: records = ...`. Текущее приложение выводит размеры от 0 до 10; после каждой непустой пачки в коде выполняется один синхронный коммит.
5. Проверить группы, распределение партиций и сохранённые offsets:

```shell
docker compose exec kafka1 kafka-consumer-groups --bootstrap-server kafka1:9092 --describe --group single-group
docker compose exec kafka1 kafka-consumer-groups --bootstrap-server kafka1:9092 --describe --group batch-group
```

В каждой группе после завершения ребалансировки должны быть два участника, между которыми распределены три партиции. Повторный запуск команд показывает продвижение `CURRENT-OFFSET`. `LAG` отражает отставание группы; во время непрерывной отправки он может меняться.

Сообщения можно посмотреть напрямую через консоль:

```shell
docker compose exec kafka1 kafka-console-consumer --bootstrap-server kafka1:9092 --topic messages --from-beginning --max-messages 10
```

Также доступен [Kafka UI](http://localhost:8080): кластер `local`, топик `messages`, сообщения и группы консьюмеров.

### Остановка

```shell
docker compose stop
```

Повторный запуск: `docker compose start`. Команда `docker compose down` удаляет контейнеры; постоянные volumes в этом проекте не настроены, поэтому после пересоздания контейнеров не следует рассчитывать на сохранность сообщений и offsets.

## Что важно учесть при проверке задания

- **Пакетный консьюмер получает до 10 записей, а не минимум 10 за каждый `poll()`.** `max.poll.records` задаёт верхнюю границу, а `fetch.min.bytes` измеряется в байтах и не гарантирует количество сообщений. Текущий код обрабатывает и коммитит также пачки меньше 10.
